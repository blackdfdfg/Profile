Base: blackdfdfg/Profile main f2259077059e962046b5881bc4765bf3311d72da. Worker source only; no extension or website changes; no migration or D1 data writes required.

## Diagnosis (2026-11-05 snapshot)
D1 analytics around 07:22 UTC showed 26,793 rows written since 00:00 UTC. At a nearby point, 1,721 credit-generation jobs had been created (1,683 committed, 35 refunded; counts vary with time). Job creation/debit/ledger, response and settlement, cleanup and rate-limiting all write. Each successful credit-auth request currently writes an IP rate-limit row; a normal credit generation + settlement makes two such writes, in addition to required wallet/ledger/job and AI-limiter writes. These are code-level contributors, not a per-query attribution of all 26,793 rows. Index maintenance also counts. Do not remove idempotency, credit ledger, refunds, settlement or indexes to lower this number.

## Change
Successful credit-key authentication uses Cloudflare's native edge rate-limiting binding instead of a D1 IP-counter write. Invalid/expired/unbound/mismatched keys still increment the globally strict original D1 rate limiter; AI per-key and refund rate limits remain unchanged. Missing/error/malformed binding falls back to original D1 behavior. Expected saving: about two logical IP counter writes per ordinary generation + settlement (plus successful balance/lookup calls); actual billable savings, throughput and latency must be measured in production. Rate limiting has a meaningful tradeoff: the native authenticated request cap is approximate and per location (600/60 sec), not the old exact globally shared 600/10 min total across valid + invalid requests. Invalid attempts still have the exact D1 600/10 min cap but are counted separately from valid requests. Review this security difference before deployment. No promise of identical limit semantics or fixed savings.

Own-API extension generation already calls the chosen AI provider directly, not the Worker credit-generate/settle endpoint per comment. Popup balances and periodic verification can still call Worker. No extension code was changed: current deployed extension source/version must be confirmed before changing popup behavior.
